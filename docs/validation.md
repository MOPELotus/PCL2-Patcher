## 自动化测试

本机 .NET SDK 8.0.426 下 Release 构建零警告、零错误，启用 warnings-as-errors；**16 项测试全部通过，零跳过**。测试基于真实官方 EXE，缺少输入会失败，不静默跳过。覆盖：

- 受限/不受限检测不写盘，五处功能修补与重新验证。
- 非目标方法及资源保持一致，独立 PEReader 读取所有方法体。
- 重复运行不改文件，备份精确一致，恢复、重复恢复、恢复后再次修补。
- 部分修补状态补全；替换后注入 I/O 异常的精确回滚、临时文件清理与重试。
- 缺少安装器、缺少泛型字段、改变捕获闭包、改变保留算法、新限制入口均拒绝。
- 备份损坏、EXE 被后续改动、备份冲突、截断输入均拒绝误覆盖。
- 官方输入缓存重用和损坏缓存拒绝。

合成变体将版本号改为 **2.100.0.0 / 3.0.0.0**，加入 NOP、改变偏移/token 与 VB 适配器编号，修补和验证通过。这仅说明相同 IL 结构的适配能力；这些不是验证过的真实 PCL 发行版。

## 独立验证器

运行固定版本 Microsoft ILVerify 8.0.0，使用微软 .NET Framework 4.8 参考程序集及从官方 EXE 提取的嵌入 DLL：

- 修补的五个方法：**5/5 通过，零 ILVerify 错误**。
- 全程序集：扫描 **6,339 个方法 / 665 个类型**；原版与修补版均报告同一处 `LoaderTask<TIn,TOut>` 构造函数的 `StackUnexpected` 泛型委托类型诊断（`Func<T0>` 对 `Func<object>`）。
- 该构造函数不是补丁目标，语义保持一致，最终写出中其诊断偏移也相同（0x44）。全程序集诊断基线一致，未出现新增诊断。不能将它描述为整个程序集零错误。

可复现命令：`python scripts/verify-il.py <原版.exe> <修补版.exe>`。完整日志生成于 `.artifacts/ilverify/`，原版与修补版分别保存，脚本要求修补方法全部通过且全程序集诊断与基线一致。

## 图形界面与实际操作的边界

本机是 Linux，检测到 NVIDIA RTX A4000、Tesla T10 和 580.178.04 驱动，已有物理 NVIDIA Xorg :97/:96。以 :97 尝试通过 Wine 9 启动修补 EXE，日志显示已加载目标 PE，但在界面启动前报告 `CLRRuntimeInfo_GetRuntimeHost Wine Mono is not installed`。本机没有可运行 PCL WPF 的 .NET Framework 4.8 环境；没有取得应用渲染器或页面截图，也没有用软件渲染替代验收。

因此以下项目**尚未端到端验证**：自动安装页实际加载和下载 Minecraft、七种整合包真实安装、版本修改实际完成、微软正版账号登录。不能凭进程启动或 IL 验证将这些操作标为成功。保留登录代码的结论来自所有非目标方法及资源的一致性检查。

Windows CI 配置额外执行 .NET Framework 下程序集加载及五个方法的 JIT 准备检查（`scripts/verify-clr.ps1`）；这也不等同于界面或网络操作验收。CI 实际结果见对应提交的 GitHub Actions 记录。

## 剩余兼容性问题

当前适配器只接受已知五处限制的完整结构及语义等价变体。未来更换编译器、重构安装器/闭包、改名、改变依赖身份、增加其他限制或删除底层方法时可能拒绝；需要取得真实新版 EXE 重新分析。当前没有 GUI，CLI 为优先实现。
